# 01 需求与范围

## 1. 背景与目标用户

**场景**：有人（下称"运营"）在闲鱼之类的平台上接视频代下载的单。
客户发来一条链接或一段分享文案（常常夹着 emoji、广告词、标题），运营需要：

1. 判断这是哪个平台、能不能下；
2. 把视频下下来（尽量高清、尽量无水印）；
3. 把成果交付给客户（发网盘链接、或直接把文件给客户）；
4. 回一句能直接粘回去的话（"下载好啦，链接是…"）。

**痛点**：平台风控（抖音的 `a_bogus` 签名、视频号不给匿名 mp4）、
短链要展开、一条链接其实是 80 集、水印要处理、客户催进度。
一张一张手工处理既慢又容易出错。

**本项目的目标**：把上面 4 步做成一条**本地流水线**，运营只需要粘贴链接、点一下。

**目标用户有两类**，需求优先级不同：

| 用户 | 关心什么 |
| --- | --- |
| **运营（主要）** | 快、稳、话术省事；客户看到的东西别出错（不能把 80 集误发成一集） |
| **自用（次要）** | 命令行能用、能指定清晰度/水印、能自己排查 |

## 2. 使用场景（User Story）

| 编号 | 场景 | 期望结果 |
| --- | --- | --- |
| S1 | 客户发来抖音分享文案（含短链） | 自动展开短链、下到**无水印**版本、回话给出交付链接 |
| S2 | 客户发来 B站合集里的一集 | **识别成整部**、可勾选要哪几集、打包交付 |
| S3 | 客户只发了一句标题（没有链接） | 用搜索引擎找到原视频再下（找不到就如实回复） |
| S4 | 客户发来微信视频号短链 | 引导去腾讯元宝解析一次，粘回解析出的链接即可下**明文 MP4** |
| S5 | 客户要求"要 1080P" / "不要水印" | 按订单指定清晰度与水印策略 |
| S6 | 客户发来 X（Twitter）链接但 yt-dlp 说没有视频 | 走镜像接口兜底拿到直链 |
| S7 | 下到的视频水印是"烧进画面"的 | 用 ffmpeg `delogo` 擦掉（**有损**，需明确选择） |
| S8 | 平台不给干净源 | **如实标注"带水印源"**，不假装处理过 |

| FR-19 | 打包成单文件 exe（含 ffmpeg） | `build_desktop.py`、`desktop.py` |
| FR-20 | 诊断命令（doctor/selftest/wxinfo/platforms/cookies） | `run.py` |

## 4. 非功能需求（NFR）

| NFR | 要求 | 现状 |
| --- | --- | --- |
| NFR-1 | **不依赖第三方付费解析服务** | 已移除 TikHub，全部自研（见第 5 节 D1） |
| NFR-2 | **自动化测试离线可跑** | 25 个测试文件 / 523 用例，网络请求全打本地 HTTP 服务器 |
| NFR-3 | **默认不改用户环境** | 不装证书、不改系统代理、不起浏览器；抓包/注入默认关 |
| NFR-4 | **隐私**：不打印 cookie 值、不留抓包原始数据 | `http.py` 只记 cookie 名；`wxproxy` 的落盘目录可一键删 |
| NFR-5 | 单文件交付（客户机器不用装 Python） | `dist/视频下载工具.exe`，115 MB（含 ffmpeg 与 64 个 DLL） |
| NFR-6 | 失败要**说人话且可操作** | 错误信息带下一步动作（见 `download_channels_url` 的错误文案） |
| NFR-7 | 关键判断不能是"猜的" | 每个平台结论都附实测证据（见 [03 文档](03-下载链路详解.md) 第 6 节） |

## 5. 产品决策记录（ADR 摘要）

> 每条都写清"为什么不做另一种"，避免以后有人把已否决的方案又提一遍。

### D1 移除 TikHub，全部自研

- **决定**：删除 `xydl/tikhub.py` 与所有 `delivery.tikhub.*` 配置。
- **原因**：付费第三方是单点依赖（额度/涨价/跑路都会直接影响交付）；而自研通道实测可用
  （抖音/TikTok 用登录态 CDP 截页面自身签名请求、快手用 GraphQL）。
- **代价**：抖音/TikTok 需要用户**登录一次**（登录态存在工具自己的 profile 里，长期有效）。
- **回归保护**：`test_module_has_no_tikhub_leftovers` 断言模块里不允许再出现任何 TikHub 符号/字样。

### D2 视频号走"元宝链路"，而不是自动驱动微信客户端

- **决定**：客户粘短链 → 提示去腾讯元宝解析一次 → 粘回带 `token` 的链接 → 一条 HTTP 请求拿**明文 MP4**。
- **原因**：视频号的 `/sph/xxx` 短链本身不带授权，服务端不会下发媒体；而元宝能把短链换成带
  `token`/`eid` 的 `finder-preview` 链接，带 token 请求同一接口即下发明文直链（无需登录、无需抓包、无需解密）。
- **为什么不自动驱动微信**：需要改客户端行为（注入/中间人），会弄坏用户的微信（实测两次），
  不该出现在面向客户的流程里。相关能力保留为**默认关闭**的本机诊断通道。

### D3 抓包/注入默认关闭

- **决定**：`run.py channels-capture` 必须显式启动；页面注入还要额外设 `XYDL_CAPTURE_INJECT=1`。
- **原因**：注入会改写客户端页面资源，实测导致视频号页面打不开（需清 CEF 缓存恢复）；
  默认关闭是对用户负责，也避免"悄悄改别人环境"。

### D4 去水印分两层，"取干净源"优先

- **决定**：默认 `watermark=auto`（优先无水印**源**）；像素级擦除只在显式选择 `delogo` 时做。
- **原因**：平台常同时给两份地址（抖音 `playwm` 与 `play`），取干净源**无损**、零算法风险；
  而 `delogo` 是插值覆盖，会留痕迹、局部画质下降。
- **默认另存**：`delogo` 默认输出 `xxx.nowm.mp4`，覆盖源文件要显式 `--in-place`（有损处理要能回退）。

### D5 不做 AI 擦水印

- **决定**：不引入 STTN/ProPainter 这类 inpaint 模型。
- **原因**：单文件 exe 会从 115 MB 涨到 500 MB+，且需要 GPU；性价比与"本地小工具"定位不符。

### D6 DRM 平台按设计拦截

- **决定**：腾讯视频/爱奇艺/优酷/芒果TV 直接识别为 DRM 并提示，不做无意义尝试。
- **原因**：这些站点的内容有 DRM，抓到的也放不出来；早点说清比"试半天再失败"体验更好。

### D7 下载选项按**订单**生效，不改全局配置

- **决定**：清晰度、水印策略、选集都放在订单 `meta` 里。
- **原因**：并发订单各选各的；改全局配置会让 A 单的选择串到 B 单上（选集串单这个 bug 真踩过）。

## 6. 明确"不做"的清单

| 不做 | 原因 |
| --- | --- |
| 自动驱动微信客户端下载 | 见 D2/D3：会破坏用户环境 |
| 注入页面/中间人抓包作为默认路径 | 同上，保留为可选诊断通道 |
| AI 像素级修复水印 | 见 D5 |
| DRM 平台破解 | 见 D6 |
| 微信公众号文章内视频 | 正文视频基本是腾讯源（DRM） |
| 云端服务化（多租户） | 当前定位是本地工具；cookie/登录态不宜上云 |
