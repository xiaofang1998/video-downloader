# 06 分支与协作

## 1. 分支模型

```
main            集成分支：始终可用（全量测试通过 + selftest 0）
 ├─ docs/*      文档：需求 / 架构 / 链路 / 测试 / 部署 / 协作
 ├─ feature/*   功能：一项能力一个分支
 └─ refactor/*  重构：不改变外部行为的大改动
```

规则：

1. **不在 main 上直接写大改动**：开分支 → 提交 → 推送 → 合并回 main（用 `--no-ff` 保留合并点）。
2. **一个分支一件事**：方便回滚，也让 `git log --graph` 能看出"哪一步带来了什么"。
3. **合并前**：`pytest -q` 全绿 + `run.py selftest` 退出码 0（见 [04 第 6 节](04-测试与验收.md)）。
   改了文档再加一步：`python tools/check_docs.py`（见第 6 节）。
4. **写文档的分支只碰文档**，避免和代码改动互相阻塞。
5. **合并进 main 后再推 main**；分支本身也推上去（便于 review 与追溯）。

## 2. 提交信息规范

```
<type>: <一句话说清做了什么>

<正文：为什么这么做、影响面、验证方式>
```

`type` 取值：`feat` 功能 / `fix` 修复 / `refactor` 重构 / `docs` 文档 / `test` 测试 / `chore` 杂项。

**正文要写"为什么"而不是"改了哪些文件"** —— 后者 `git diff` 已经说了。
举两个本仓库的真实例子：

```
fix: 链式上游代理解析（曾导致用户整机断网）

上游写 "http://127.0.0.1:7897" 时，旧实现直接 rpartition(":") 拿到主机名
"http://127.0.0.1"，于是每条非目标请求都 getaddrinfo 失败 —— 用户感觉"网断了"。
现在按 URL 解析并补了 7 条参数化用例 + 自动自愈 + --restore。
```

```
docs: 补全架构与代码地图（38 个源文件逐个说明）
...
```

## 3. 本次"多分支提交"的做法（可复现）

文档按主题拆成 5 个分支，每个分支一个提交，依次合并回 main：

```bat
:: ① 建分支并提交该主题的文档
git checkout -b docs/requirements main
git add docs/README.md "docs/01-需求与范围.md"
git commit -F <提交信息文件>
git push -u origin docs/requirements

:: ② 合并回 main（--no-ff 保留合并点，方便看出"这一步引入了什么"）
git checkout main
git merge --no-ff docs/requirements -m "merge: docs/requirements —— 文档索引与需求说明"
git push origin main

:: ③ 下一个主题从**最新的 main** 开分支（避免基于旧点产生冲突）
git checkout -b docs/architecture main
...
```

**为什么每个分支都从最新 main 开**：主题之间可能都改 `docs/README.md`（索引），
从旧点开会冲突；从最新 main 开则天然线性。

**历史能力的分支锚点**：为让"每项能力"在分支列表里可追溯，给已完成的提交挂了分支指针
（`git branch <名字> <sha>`，不产生新提交）：

```bat
git branch feature/platform-coverage 3d95044
git branch refactor/drop-tikhub 2b6428e
git branch feature/watermark-and-options 62ae578
git branch docs/readme-rewrite 0bad1f4
git push origin feature/platform-coverage refactor/drop-tikhub ^
                feature/watermark-and-options docs/readme-rewrite
```

## 5. 以后怎么协作

```bat
:: 1) 开分支（从最新 main）
git checkout main && git pull
git checkout -b feature/某个能力

:: 2) 开发 + 自测
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe run.py selftest

:: 3) 提交（信息按第 2 节）
git add -A
git commit -F <信息文件>

:: 4) 推送分支
git push -u origin feature/某个能力

:: 5) 合并回 main（本地单人开发可直接 merge；多人协作走 PR）
git checkout main
git merge --no-ff feature/某个能力 -m "merge: feature/某个能力 —— <一句话>"
git push origin main
```

**代码评审关注点**（按本仓库的实际教训）：

| 关注 | 为什么 |
| --- | --- |
| 是否引入新的外部依赖/付费服务 | 见 [01 D1](01-需求与范围.md)：不引入付费单点 |
| 是否默认改了用户环境（证书/代理/浏览器） | 见 [01 D3](01-需求与范围.md) |
| 订单级选项是否走 `meta` | 全局配置会串单 |
| 错误信息是否给下一步动作 | 面向非技术的使用者 |
| 新踩的坑有没有补测试并在 docstring 写清原因 | 这是本仓库最重要的"文档" |
| 是否新增了 `git grep -i tikhub` 命中 | 有回归测试挡着，但评审时也看一眼 |

## 6. 文档自检

文档里写错一个文件名或测试名，比不写更糟 —— 接手的人会照着做，然后发现根本不存在。
所以仓库里带了一个自检脚本：

```bat
python tools\check_docs.py      :: 退出码 0 = 文档里提到的东西都真实存在
```

它检查四类引用：

| 检查 | 内容 |
| --- | --- |
| 内部链接 | `[文字](路径)` 指向的本地文件必须存在 |
| 源码引用 | 反引号里的 `xydl/…`、`tests/…` 路径必须存在（白名单：已删除的 `xydl/tikhub.py`、分支名） |
| 测试名引用 | 反引号里的 `test_xxx` 必须在 `tests/` 里真实存在 |
| 子命令引用 | 反引号里 `run.py <cmd>` 必须在 `run.py` 注册过 |

**本次就是靠它抓到错误的**：文档里凭印象写的三个测试名（取消竞态、证书并发、代理前缀事故）
一个不存在、一个名字记错，改正后才合并。
所以**引用具体的文件名/测试名/命令时，一律先跑这个脚本**。
